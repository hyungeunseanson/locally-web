# LOCALLY 결제 PHASE 2: 구현 증거와 운영 전 적용 순서

## 기준 및 범위

- 구현 기준 GitHub `main`: `905bb105187118d99e4d4a961f77a47512c04f49` (2026-10-11 KST 작업 시작 시 조회).
- 같은 시점 Cloudflare Production Worker `locally-web-opennext-production`의 활성 버전은 `fdc729a3…` 100%였고 배포 메모의 소스 SHA도 `905bb105…`였다. 이 문서는 Production 변경 기록이 아니다.
- 체험 NICEPAY 일반 카드 결제만 새 복구 원장을 사용한다. 기존 PHASE 1 대상 거래, PortOne, 서비스·대리 예약, 환불·정산의 별도 경로는 유지한다.
- NICEPAY 운영 결제·환불은 테스트하지 않았다. PGlite 격리 DB와 Mock HTTP를 사용했다.

## 결제 증거와 경계

1. 카드 결제 Claim과 주문번호·금액·MID 복구 원장 생성은 하나의 DB 트랜잭션에서 확정한다. 원장 쓰기 실패 시 Claim도 롤백된다. 테이블과 이벤트 원장은 서비스 역할만 접근한다.
2. NICEPAY 인증 응답의 서명·TID·MID·주문번호·금액을 확인하고 TID를 영속 저장한 뒤에만 승인 API 호출권을 원자적으로 획득한다. 같은 콜백은 두 번째 승인 API를 호출할 수 없다.
3. 승인 API 응답의 TID·MID·주문번호·금액·서명을 재검증하고 승인 증거를 원장에 먼저 보존한다. 그 다음 기존 예약 확정 RPC를 실행한다. DB 확정에 실패해도 원장에는 승인 증거가 남는다.
4. NICEPAY의 거래조회 API는 TID와 승인 상태만 제공한다. 주문번호·금액·MID는 앞의 서명된 응답 및 DB의 시도 원장과 대조한다. 재조회에서는 요청한 TID와 응답 TID도 일치해야 한다. 거래조회 실패는 미결제 증거로 취급하지 않는다.
5. 재시도는 기본 2·4·8·16분 간격이며, 5회 실패 또는 신원 충돌·취소 후 승인 등은 `manual_review`로 전환한다. 관리자 알림과 이메일을 발송한다. 자동 승인취소·환불은 새로 실행하지 않는다.
6. 서버 복구는 기존 10분 주기 Cron에 독립 작업으로 연결했다. 다른 운영 감지 작업이 실패해도 복구 작업은 실행된다. 기한이 된 거래를 DB에서 먼저 선별하고 실행당 최대 20건을 처리한다. `NICEPAY_RECOVERY_SCHEDULED_ENABLED=true`가 코드와 배포 계약의 기본값이다.

## 좌석 반환 규칙

| 상황 | 처리 |
| --- | --- |
| 창 닫힘·일반 오류 직후 TID를 받지 못함 | DB에 승인 시작 기록이 없는 동일 시도만 원자적으로 즉시 해제 |
| 인증 TID는 있으나 승인 시작 전 | NICEPAY에서 거래 부재 또는 취소 확인 후 해제. 조회 장애면 보류 |
| 5분 결제창 제한 | 같은 검증으로 해제하거나 보류 |
| 승인 시작 후 결과 불명확 | 좌석 유지, NICEPAY 재조회 및 재시도 |
| 승인 상태 확인 | 기존 예약 확정 RPC로 멱등 확정 |
| 브라우저 종료 | 10분 Cron이 서버 원장을 재검사 |
| 기존 30분 자동 정리와 경합 | 양쪽이 예약 행 잠금을 획득하고 상태·시도 단계를 검사. 승인 진행 중인 좌석은 PHASE 2가 해제하지 않음 |

5분은 브라우저 결제창 대기 제한이며, 기존 30분 좌석 점유 정책은 유지한다. 브라우저가 살아 있고 인증 전 단계라면 창 닫힘 요청 후 즉시 반환을 시도한다. 브라우저가 종료되면 Cron 주기와 NICEPAY 조회 결과에 따라 반환 시점이 달라진다. 승인 상태가 불명확하면 반환 시점을 보장하지 않는다. 무통장 체험 예약의 DB 만료 12시간은 변경하지 않았고, 결제·완료 화면과 FAQ의 한국어·영어·일본어·중국어 안내를 맞췄다.

## 운영 적용 절차와 출시 Gate

1. PR CI 통과와 코드 리뷰를 확인하고, 배포 직전 GitHub `main` 및 Production Worker의 실제 소스 SHA와 환경 설정을 다시 조회한다. 다른 변경이 생기면 새 소스와 Migration 충돌을 재검증한다.
2. 운영 DB 백업·복구 지점을 확인한 뒤 `20261010172837_experience_nicepay_recovery.sql`을 먼저 적용한다. 서비스 역할 외 접근 차단, 새 테이블·RPC, 기존 결제·정산 데이터 불변을 확인한다.
3. 검증된 PR 소스를 병합한 뒤 Production Worker를 배포한다. 배포 스크립트와 Wrangler의 복구 Cron 기본값은 `true`로 고정했으며, 배포 계약 검사에서 실제 플래그 변화를 확인한다. Canary 격리를 유지한다.
4. 비금융 합성 점검으로 Worker 버전·트래픽, DB RPC 접근 제어, Cron 실행 기록, 관리자 원장 화면, 12시간 안내를 확인한다. 실제 운영 결제를 테스트 결제로 만들거나 자동 환불하지 않는다.
5. 실패 시 우선 `NICEPAY_RECOVERY_SCHEDULED_ENABLED=false`로 Cron만 중지하고 원장·이벤트를 보존한다. 필요하면 검증된 이전 Worker를 재배포한다. Migration은 과거 Worker에 영향을 주지 않는 추가 스키마이므로 성급히 삭제하지 않는다. `manual_review` 항목은 NICEPAY 관리자 거래 내역과 DB를 사람이 대조한다.

## 로컬 검증

- 격리 PGlite 13건: Claim/원장 부분 실패 롤백, 160건 오래된 원장의 새 장애 기아 방지, 정상 승인·확정, DB 장애 후 재시작, 불명확한 승인, 중복 TID, 닫힘, 5분 제한, 승인 중 해제 거절, 재실행, 금액·MID·주문번호 충돌, 늦은 승인, RLS.
- Mock HTTP 및 런타임 검증: 서명, 거래조회 상태·네트워크 오류, 예약 확정 재시도, 고객·Cron 중복 요청, 다른 Cron 작업 실패 시 독립 실행.
- 기존 환불·취소 통보 회귀 37건, 기존 예약 결제 claim 계약 및 Cloudflare 배포 계약, TypeScript·ESLint를 PR CI에서 반복 확인한다.

NICEPAY 거래조회 API가 주문번호·금액·MID를 돌려주지 않으므로, 인증/승인 증거를 받지 못한 과거 거래는 자동 확정하지 않고 운영자 대조 대상으로 남긴다. 새 복구 원장은 승인 취소·환불을 수행하지 않는다.
