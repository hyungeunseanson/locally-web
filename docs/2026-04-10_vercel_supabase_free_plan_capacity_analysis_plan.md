# Vercel + Supabase 무료 플랜 수용량 분석 계획

## 문서 성격
- 실행 전 준비 문서
- 실제 수용량 계산 결과 없음
- 코드 변경 없음
- 공식 무료 플랜 한도 수치도 분석 시작 시점에 다시 확인 후 확정

## 분석 목적
- 현재 서비스 코드베이스를 기준으로, Vercel + Supabase 무료 플랜에서 어느 수준까지 운영 가능한지 나중에 정량 분석하기 위한 준비 문서다.
- 결과물은 추상 설명이 아니라 `호스트 수 / 체험 수 / 고객 MAU / 피크 동시성` 기준의 숫자 범위로 제시하는 것을 목표로 한다.
- 최종 분석에서는 현재 구조에서 어떤 자원이 먼저 병목이 되는지 찾고, 그 병목을 기준으로 안전 운영 가능 범위와 위험 구간을 분리해 제시한다.

## 공식 문서 확인 원칙
- Vercel / Supabase는 반드시 최신 공식 문서만 사용한다.
- 예전 기억, 블로그, 커뮤니티 글, 서드파티 요약 자료는 근거로 사용하지 않는다.
- 무료 플랜 수치는 실제 분석을 시작하는 시점에 다시 확인한 뒤 확정한다.
- 동일 서비스의 여러 공식 문서 간 수치 표현이 다를 경우 더 보수적인 값을 기준으로 사용하고, 차이가 있음을 짧게 설명한다.
- 최종 보고서에는 사용한 공식 문서 링크를 반드시 함께 남긴다.

## 분석 방법
1. 공식 무료 플랜 한도를 먼저 최신 기준으로 확인한다.
2. 현재 코드베이스에서 실제 자원 소모 경로를 구조별로 분해한다.
3. 공개 페이지, 예약, 채팅/알림, 호스트 운영, 관리자/보조 기능으로 나눠 호출 패턴을 파악한다.
4. DB, Storage, Egress, Realtime, MAU, Vercel transfer, functions, middleware, build/cron 중 어떤 축이 먼저 닿는지 병목 우선순위를 도출한다.
5. 계산 전제값을 정하고, 각 전제에 따라 낙관 / 현실 / 보수 시나리오를 만든다.
6. 이론상 최대치와 실제 안전 운영 권장치를 분리해 제시한다.
7. 무료 플랜 유지 가능 여부와 업그레이드 추천 시점을 숫자 기준으로 정리한다.

## 계산 전제
- 호스트당 평균 체험 수
- 체험당 평균 이미지 수
- 이미지 평균 압축 후 크기
- 체험당 availability 슬롯 수
- 고객 1명당 월간 홈 조회 수
- 고객 1명당 월간 검색 조회 수
- 고객 1명당 월간 상세 조회 수
- 예약 시도율
- 채팅 발생률
- 문의 1건당 평균 메시지 수
- 로그인 사용자 비율
- 관리자/운영 화면 부하는 핵심 수용량 산정과 분리하고 별도 보정치로만 반영

## 산출물 형식
1. 현재 무료 플랜 기준 공식 한도 요약
2. 우리 서비스에서 먼저 닿을 가능성이 큰 병목 TOP 3
3. 대략 수용 가능 규모
   - 호스트: 약 몇 명
   - 체험: 약 몇 개
   - 고객: 월간 활성 사용자 기준 약 몇 명
4. 전제 조건
5. 낙관 / 현실 / 보수 시나리오 3가지
6. 무료 플랜 유지 가능 여부 결론
7. 유료 전환 시점 추천 기준
8. 가장 작은 비용으로 오래 버티는 최적화 제안

## 검증 기준
- 공식 문서 링크를 반드시 함께 남길 것
- 각 숫자마다 계산 근거를 붙일 것
- DB / Storage / Egress / Realtime / MAU / Vercel transfer / functions / middleware 영향을 각각 확인할 것
- 이미지 저장량과 이미지 전송량을 분리해서 볼 것
- 이론상 최대치와 실제 안전 운영 권장치를 분리할 것
- MAU와 별개로 피크 동시성도 따로 볼 것
- 낙관 / 현실 / 보수 시나리오가 서로 다른 가정값을 갖도록 명확히 구분할 것

## 가정사항
- 운영 외 테스트 산출물, 로그, 리포트 파일, 로컬 개발 전용 파일은 계산에서 제외한다.
- admin 전용 화면은 핵심 수용량 산정의 주축이 아니므로 보정 부하로 처리한다.
- cron은 실제 스케줄 등록 여부와 별개로 구조상 존재 여부를 반영하되, 실제 사용량은 별도로 확인한다.
- 이미지 전송은 Supabase Storage egress와 Vercel transfer를 분리해 계산한다.
- 결과 리포트는 이번 문서와 분리된 별도 산출물로 작성한다.

## 추가 보정 사항
- 공식 한도는 실제 분석 시작 시 먼저 다시 확인 후 확정한다.
- MAU뿐 아니라 피크 동시성도 별도 분석한다.
- 이미지 저장량과 egress/transfer를 분리 계산한다.
- 이론상 최대치와 실제 안전 운영 권장치를 분리 제시한다.
- realtime은 연결 수와 메시지 수를 구분해 분석한다.
- SSR / CSR / API route / middleware가 각각 어느 자원을 사용하는지 나눠서 판단한다.
- 홈, 검색, 상세, 예약, 채팅, 호스트 화면, 관리자 화면의 호출 패턴을 합산하되 핵심 사용자 흐름과 운영성 부하를 분리한다.

## 나중에 실행할 때 우선 확인할 공식 항목

### Supabase
- DB 용량
- Storage 용량
- Egress / bandwidth
- MAU
- Realtime messages
- Realtime peak connections
- Auth 관련 사용량 및 제한

### Vercel
- Fast Data Transfer / bandwidth
- Edge Requests
- Function Invocations
- Active CPU
- Memory
- Build limits
- Cron limits
- Image Optimization limits

## 나중에 실행할 때 우선 확인할 코드 영역
- 홈 / 리스트 / 검색 / 상세
- 예약 / 결제 진입 / 예약 생성
- 채팅 / 알림 / realtime / presence
- 호스트 dashboard / availability / 목록 조회
- middleware / SSR layout / auth session refresh

## 실행 시 유의사항
- 이번 문서를 기준으로 다음 작업에서는 실제 최신 공식 문서를 먼저 재확인한 뒤에만 숫자 계산을 시작한다.
- 계산 결과를 먼저 만들지 말고, 공식 한도와 코드 구조 근거를 표 형태로 정리한 다음 산정에 들어간다.
- 숫자는 반드시 범위로 제시하고, 안전 운영선과 위험 구간을 따로 적는다.
