Cloudflare's documented
[Get Worker Version](https://developers.cloudflare.com/api/resources/workers/subresources/beta/subresources/workers/subresources/versions/methods/get/)
accepts an exact UUID and `include=modules`, returning that version's ID,
`main_module`, and base64 module contents. Although the provider supports `latest`
and UUID prefixes, this implementation forbids them. This is a beta provider API;
unavailability/schema changes fail closed without falling back to script content.

## New contract

A shared GET-only reader performs:

1. Read latest deployment; require valid identity/timestamps and exactly one
   version at numeric 100%. Uploaded candidates outside this distribution do not
   matter. An actual multi-version distribution, including an explicit zero-percent
   entry, remains blocked by the existing pre-release single100 invariant.
2. Read the exact active version's metadata and script ETag/DO handlers.
3. Request `/workers/{name}/versions/{exactUUID}?include=modules`; require the
   returned UUID, unique module names, one unambiguous JavaScript main module,
   canonical base64 and valid UTF-8. Never read `/content/v2` or `latest` as fallback.
4. Re-read version metadata and deployment, rejecting ETag/handler/ID/distribution
   changes. Return a SHA256 of the exact main-module bytes. Raw source is
   non-enumerable, never written as evidence or logged; provider errors are redacted.
5. Use these same bytes for bridge token extraction and complete DO fingerprints.
   Before deploy, fetch the exact version source again and match deployment,
   version, ETag, artifact digest and bridge lineage against the build proof.
   Candidate contract also cross-checks the bridge and DO proof identities/digests.

The receipt is not a newly trusted external attestation: it is local, hash-only
build evidence revalidated against the authenticated version-specific API. Old
ETag-only receipts are rejected and must be regenerated by the official build.
No static current version IDs/ETags are introduced into executable code.

## Safety and operational costs

DOQueueHandler/DOShardedTagCache structural comparison, only four reviewed
build-state differences, Next authentication, cross-version runtime matrix,
export/binding/migration invariants, explicit candidate mode/approvals and final
freshness gate remain. No uploader/promoter adapters are added.

Each source verification uses five bounded GETs (deployment, metadata, modules,
metadata, deployment), each with the existing 30-second bound, no extra retries
and redirects forbidden. Final freshness now downloads the roughly 31 MB active
main module again. This is operator-time release traffic, not application traffic;
it avoids trusting a stale local hash. The final GET-to-deploy window still exists,
so the existing serialized release operating rule remains necessary.
